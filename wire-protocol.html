PostgreSQL Wire Protocol Reference

This is a LLM-generated compilation of PostgreSQL 19, Chapter 54. Frontend/Backend Protocol and Section 32.5. libpq Pipeline Mode.
Streaming and logical replication are out of scope.

Protocol Overview

  • Transport: TCP/IP or Unix domain sockets, default port 5432
  • Byte order: network byte order (big-endian) for all integers
  • Roles: the client is the frontend (F) and the server process is the backend (B)

Message Framing

  • Type: a single ASCII character. The same byte can mean different messages in each direction; see Message Index.
  • Length: Int32 counting itself and the payload, but not the type byte. An empty message has length 4.

Exceptions to this framing:

  • StartupMessage, SSLRequest, GSSENCRequest and CancelRequest have no type byte. They start with the length.
  • The replies to SSLRequest and GSSENCRequest (S, G or N) are a single unframed byte.
  • GSSAPI handshake tokens and encrypted packets use their own framing; see Session Encryption.

Message Data Types

This page uses the notation from the official documentation.

The documentation does not assign a signedness to Intn. Read value lengths as signed, since -1 means NULL. Read object IDs as unsigned, since the oid type is an unsigned 32-bit integer.

Format Codes

  • 0 = text: the string produced and accepted by the data type's output and input functions. On the wire it has no trailing null byte, and it cannot contain embedded null bytes.
  • 1 = binary: a type-specific representation. Integers are in network byte order. Representations of complex types can change between server versions.

All other codes are reserved.

Connection Startup

In the diagrams on this page, a dashed arrow is a message that is not always sent, and a box shows exactly which messages its label applies to. Asynchronous messages are not drawn: once startup has finished, NoticeResponse, ParameterStatus and NotificationResponse can arrive between any of the drawn messages. See Asynchronous Messages.

Code the startup phase as a state machine that accepts any of these messages when it could make sense. Do not hard-code this exact sequence.

Session Encryption

Encryption is requested before StartupMessage. The protocol cannot force it, so a client that requires encryption must close the connection when the server declines. A server administrator can separately reject unencrypted sessions during authentication.

SSLRequest (no type byte)

TypeDescription
Int32(8)Length
Int32(80877103)SSL request code

The server replies with one of:

  • S (one byte): perform the TLS handshake, then send StartupMessage inside TLS.
  • N (one byte): the server is unwilling. The client may close, send StartupMessage unencrypted, or send GSSENCRequest instead.
  • ErrorResponse: close the connection. Do not show the message to the user, because the server is not authenticated yet (CVE-2024-10977). The client may open a fresh connection without requesting SSL.

Read exactly one byte before handing the socket to the TLS library, or treat any extra buffered bytes as a protocol violation. Extra bytes may be a man-in-the-middle buffer-stuffing attack (CVE-2021-23222).

Starting the TLS handshake without waiting for the reply saves a round trip, but if the server replies N it simply disconnects.

Direct TLS

A client can start the TLS handshake immediately without SSLRequest, then send StartupMessage inside TLS. The client must use ALPN with the protocol name postgresql (RFC 7301). This mode cannot negotiate GSSAPI or fall back to an unencrypted connection. The server refuses any other encryption request on such a connection.

GSSENCRequest (no type byte)

TypeDescription
Int32(8)Length
Int32(80877104)GSSAPI encryption request code

The server replies with G, N, or ErrorResponse. N and ErrorResponse are handled as for SSLRequest, and the one-byte read rule also applies. After N, the client may send SSLRequest instead.

After G:

  1. Call gss_init_sec_context() in a loop, starting with empty input and then using each server result, until it returns no output. Prefix each token sent to the server with its length as an Int32.
  2. Encrypt StartupMessage and all later data with gss_wrap(), prefixing each result with its length as an Int32.
  3. Keep encrypted packets under 16 kB, which is the limit the server accepts. Use gss_wrap_size_limit() to split larger messages across gss_wrap() calls. The server will not send packets larger than 16 kB.

Version and Extension Negotiation

StringOption name

The server sends this when it does not support the requested minor version, or when the startup message contains an unrecognized _pq_. option. If it is not sent, the server supports the requested version and every requested option.

  • This message does not end the connection. Authentication continues on the same connection using the version the server indicated.
  • If the client cannot use that version, or needs a rejected option, it should close the connection immediately.
  • If the server does not support the requested major version, it rejects the connection with ErrorResponse. A server may also reject an unsupported minor version instead of negotiating.
  • Messages use the layouts of the negotiated version, which affects the secret key size in BackendKeyData and CancelRequest.

No _pq_. extensions are currently defined. _pq_.test_protocol_negotiation is reserved for greasing, and all other names are reserved for future use.

The version field holds the full version number, not a bare minor number: a request for 3.9999 returns 196610 (0x00030002). The server sent this message before the first Authentication message. The documentation also allows it after AuthenticationOk, so accept it in both places.

SASL Authentication

PostgreSQL implements three mechanisms: SCRAM-SHA-256, SCRAM-SHA-256-PLUS and OAUTHBEARER. More may be added, so ignore names the client does not support.

  1. The server sends AuthenticationSASL with its mechanism list.
  2. The client sends SASLInitialResponse with its chosen mechanism and any initial response.
  3. One or more rounds of AuthenticationSASLContinue and SASLResponse follow.
  4. The server sends AuthenticationSASLFinal only if the mechanism defines completion data, then AuthenticationOk.

The server can abort at any stage with ErrorResponse.

SCRAM-SHA-256

Defined by RFC 5802 and RFC 7677.

MessageSCRAM content
SASLInitialResponseclient-first-message: <gs2-header>n=,r=<client-nonce>
AuthenticationSASLContinueserver-first-message: r=<combined-nonce>,s=<salt-base64>,i=<iterations>
SASLResponseclient-final-message: c=<binding-base64>,r=<combined-nonce>,p=<proof-base64>
AuthenticationSASLFinalserver-final-message: v=<server-signature-base64>

The GS2 header and the c= value depend on the channel binding choice:

SituationMechanismGS2 headerc= value is base64 of
Client does not support channel bindingSCRAM-SHA-256n,,n,, (biws)
Client supports it, but the server did not offer -PLUSSCRAM-SHA-256y,,y,, (eSws)
Client uses channel bindingSCRAM-SHA-256-PLUSp=tls-server-end-point,,GS2 header followed by the certificate hash

PostgreSQL's only channel binding type is tls-server-end-point (RFC 5929). The certificate hash covers the server's DER certificate, using the certificate's signature hash algorithm, or SHA-256 if that algorithm is MD5 or SHA-1. A client should prefer -PLUS when it can use it.

The proof and signature calculation:

SaltedPassword  = PBKDF2-HMAC-SHA-256(password, salt, iterations)
ClientKey       = HMAC(SaltedPassword, "Client Key")
StoredKey       = SHA-256(ClientKey)
AuthMessage     = client-first-message-bare + "," + server-first-message + ","
                  + client-final-message-without-proof
ClientSignature = HMAC(StoredKey, AuthMessage)
ClientProof     = ClientKey XOR ClientSignature
ServerKey       = HMAC(SaltedPassword, "Server Key")
ServerSignature = HMAC(ServerKey, AuthMessage)

Here client-first-message-bare is the client-first-message without its GS2 header. PostgreSQL differs from the SCRAM specifications in two ways:

  • User name: the server ignores n= and uses the name from StartupMessage, so n= can be empty.
  • Password: the server applies SASLprep when a password is set, but keeps the raw bytes if the password is not valid UTF-8 or contains sequences that SASLprep prohibits. A client must prepare the password the same way to derive the same key.

The client must check that the combined nonce starts with its own nonce, and must compare v= with its computed ServerSignature before trusting AuthenticationOk.

The documentation ties SCRAM-SHA-256-PLUS to the server build, but the server source (auth-scram.c) advertises it only on a connection that is using TLS.

OAUTHBEARER

Defined by RFC 7628. It has no channel binding variant and no AuthenticationSASLFinal. The initial response is a GS2 header followed by key/value pairs; the server only uses the auth key, which holds the bearer token, and currently ignores the GS2 authzid and the host and port keys. A client with no token uses two connections:

  1. Discovery: send SASLInitialResponse with an empty auth value. The server replies with AuthenticationSASLContinue holding an error status, a well-known URI and scopes. The client answers with a SASLResponse holding the single byte 0x01, and the server fails the exchange with ErrorResponse.
  2. Reconnect: after obtaining a token by any OAuth flow, send it in auth. If the client is authorized, the server replies with AuthenticationOk.

After AuthenticationOk

The client sends nothing until ReadyForQuery. The server can still fail startup with ErrorResponse, or send NegotiateProtocolVersion or NoticeResponse. Normally it sends ParameterStatus messages, BackendKeyData, then ReadyForQuery.

The secret key is always 4 bytes before protocol 3.2. From 3.2 it is 4 to 256 bytes. PostgreSQL sends at most 32 bytes, and middleware may use longer keys, so the client must not assume a fixed size. Third-party servers without cancellation support may omit BackendKeyData.

ParameterStatus is described under Asynchronous Messages.

All ParameterStatus messages came before BackendKeyData. The key was 32 bytes under protocol 3.2 and 4 bytes under 3.0.

An error can occur partway through a statement's messages. ErrorResponse aborts the rest of the query string, and ReadyForQuery always follows. Values are in text format, unless the statement is a FETCH from a cursor declared BINARY; the format codes in RowDescription show which applies.

Multiple statements in one Query

  • Without explicit transaction control, the statements run in one implicit transaction block, which commits at the end of the message or rolls back on error.
  • A COMMIT or ROLLBACK closes the current block. Any following statements run in a new implicit block. In an implicit block, the server also issues a warning, since there was no matching BEGIN.
  • If an earlier message already opened a block, the Query continues it, however many statements it holds, and nothing commits at the end of the message unless the string commits it.
  • A BEGIN starts a regular block that stays open across messages until an explicit COMMIT or ROLLBACK. Earlier statements in the same message join it.
  • Execution stops at the first error, so BEGIN; SELECT 1/0; ROLLBACK; leaves the session in a failed block, and another ROLLBACK is needed.
  • The whole string gets lexical and syntax analysis before anything runs, so a syntax error in a later statement prevents all of them from running. Errors found at semantic analysis or later, such as a misspelled table name, do not have this effect, so earlier statements can already have committed.
  • Savepoints are not allowed in an implicit block.
  • All statements in the message see the same statement_timestamp().

Extended Query Protocol

This protocol splits a query into separate steps. Parse creates a prepared statement from query text. Bind creates a portal from a statement and parameter values. Execute runs a portal. Both object types exist in unnamed and named forms and belong to one session. Unnamed objects are optimized for running a query once, and named objects for repeated use.

Replies are not delivered one message at a time. The server combines its output into as few packets as it can, so a client that sends Parse and waits for ParseComplete without sending Flush or Sync can wait forever.

Unlike simple Query, Execute does not produce RowDescription or ReadyForQuery. Send Describe before Execute to learn the row layout.

A client can also read results before Sync and fetch a portal in parts. Flush makes the replies arrive without ending the transaction, so the portal stays open across the fetches:

The documentation says that closing a statement also closes portals built from it.

A portal bound from a statement still executed after that statement was closed in the same transaction. Close portals explicitly, and do not rely on either behaviour.

Sync

Marks the end of a series of extended-query messages. If the session is not in a BEGIN block, Sync closes the current transaction, committing on success and rolling back on error. Inside a BEGIN block, the transaction stays open. The reply is ReadyForQuery, whose status byte shows which case applies. Each Sync produces exactly one ReadyForQuery.

Flush

Forces the server to deliver pending output. It produces no message of its own, does not end a transaction, and does not cause ReadyForQuery. It is needed after any extended-query command other than Sync if the client wants to see the results before sending more.

Error Recovery

When any extended-query message fails, the server sends ErrorResponse, then reads and discards all messages until Sync, then sends ReadyForQuery. No skipping happens if the error occurs while processing Sync itself, which keeps the one-to-one match between Sync and ReadyForQuery.

SQL can reach the same objects: DECLARE CURSOR and FETCH use named portals, and PREPARE and EXECUTE use named prepared statements.

A simple Query message behaves approximately like Parse, Bind, portal Describe, Execute, Close and Sync on the unnamed objects, without ParseComplete, BindComplete, CloseComplete or NoData.

Pipelining

Pipelining means sending further queries without waiting for earlier ones to finish, which reduces network round trips. There is no pipeline message or server mode; the client sends ordinary extended-query messages. The server starts executing commands as they arrive and returns results in the order received.

Segments

Each Sync ends one segment of the pipeline. Without an explicit BEGIN, the commands in a segment form one implicit transaction block, so a failure rolls back the whole segment and skips the rest of it. Segments that must commit independently are separated by Sync. The server only detects the implicit block when the first command ends without a Sync.

This example uses statements that return no rows and sends no Describe. Those replies follow the Extended Query diagram.

Transaction outcomes

PipelineOn errorStatus at Sync
No BEGINThe earlier commands in the segment roll back and the later ones are skipped. The next segment starts clean.'I'
BEGIN ... COMMIT in one segmentSame, but COMMIT is skipped too, so the block stays failed. Later commands fail with 25P02 until ROLLBACK.'E'
Several explicit transactions in one segmentTransactions already committed stay committed. The current one aborts, and the following ones are skipped.'E' if a block is still failed, otherwise 'I'

Skipping applies to every command until Sync, even one that would roll back the transaction, so a ROLLBACK in the same segment does not run.

Work is committed only once the client receives the CommandComplete for COMMIT (or the ReadyForQuery for an implicit commit), not when the client sends it. Since errors arrive later, the client must be able to resend work done after the last confirmed commit.

The tests confirmed 'I' with the earlier insert rolled back in the first row, and 'E' then 25P02 in the second row.

Client requirements

  • Detect completion by counting ReadyForQuery against the number of Syncs sent. Skipped commands produce no messages, so counting command responses is unreliable.
  • Match results with a FIFO queue of what was sent, because messages carry no request ID.
  • Read while writing. The server blocks when it cannot send results, and the client blocks when it cannot send queries. If the client sends enough to fill both directions before reading, the two deadlock. Use non-blocking I/O or a separate read path for large pipelines.
  • Send Flush or Sync before waiting for any result.

Restrictions and edge cases

  • A later command can depend on an earlier one in the same pipeline, such as using a table it creates or a statement it prepares.
  • Commands that cannot run in a transaction block, such as CREATE DATABASE, fail in a pipeline unless they are the first command after a Sync. On success they force an immediate commit, so a Sync directly after one only produces ReadyForQuery.
  • libpq's pipeline mode forbids simple Query, multi-statement strings and COPY. This is a libpq rule. At the protocol level, the server still processes a Query message that arrives while earlier commands are unfinished.
  • An error in a simple Query does not skip later messages, because skipping applies only to extended-query errors. While the server is skipping after an extended-query error, it also discards Query messages.

Sending three Query messages at once, where the second failed, produced three ReadyForQuery messages, and the third query still ran.

When it helps

Pipelining helps most with high latency and many small operations: a 100-statement operation at 300 ms round-trip time spends 30 s on network latency sequentially and as little as 0.3 s pipelined. It helps little when each query takes much longer than a round trip. It does not help when the client needs one result to produce the next command, since that requires a full round trip.

COPY Protocol

COPY can start from a simple Query or an Execute. When it ends, the server returns to the protocol that started it. After a Query, ReadyForQuery follows automatically. After an Execute, ReadyForQuery comes only in reply to a later Sync.

Copy-out (COPY ... TO STDOUT)

  • On a server-side error, ErrorResponse replaces the remaining messages and ends copy-out mode. No CopyDone is sent.
  • NoticeResponse and ParameterStatus can arrive between CopyData messages, and the client should be prepared for other asynchronous messages too. Any other message type may be treated as ending copy-out mode.
  • The client cannot stop the transfer except by cancelling or closing the connection, but it can discard the data.

Copy-in (COPY ... FROM STDIN)

  • CopyData boundaries do not need to match row boundaries.
  • CopyDone ends the copy successfully. CopyFail makes the COPY statement fail with an error.
  • A client that is not prepared to supply data, such as a generic query API that receives an unexpected CopyInResponse, must send CopyFail. The server is waiting for input until it does.
  • After an error, the server discards the rest of the Query message or skips to Sync. Any CopyData, CopyDone or CopyFail the client is still sending is dropped.
  • Flush and Sync are ignored during copy-in, including those a client library sends right after Execute. After CopyDone, an extended-protocol client must send a new Sync to receive ReadyForQuery.
  • Any other message type is a protocol error.
CopyFail
TypeDescription
Byte1('f')Message type
Int32Length
StringError message to report as the cause of failure

The documentation says other message types abort copy-in, but sending Query or Parse during copy-in produced ERROR 08P01 and then FATAL 08P01, and the server closed the connection. CopyFail produced ERROR 57014 and kept the session open.

Copy-both

Used only for streaming replication, after START_REPLICATION on a walsender connection. Both sides can send CopyData until one sends CopyDone, after which the connection is in copy-in or copy-out mode for the remaining direction. After both sides have sent CopyDone, copy mode ends and the server returns to command processing. After a server-side error, the server discards messages until Sync. The client should treat ErrorResponse as ending the copy in both directions and must not send CopyDone.

The overall format is 0 for both text and csv, so these messages cannot tell the client which one is in use. All columns in one operation currently share a format, but the message design does not assume this.

The documentation says each backend CopyData holds one row, but there are exceptions. Binary COPY puts the file header and first row in the first CopyData, and the trailer in its own message. FORMAT json reports overall format 0 and 1 column regardless of table width, and with force_array sends each bracket as its own CopyData.

Text format

  • One line per row. Rows end in \n on output. On input, \n, \r or \r\n are accepted, but must be used consistently. COPY FROM raises an error if a line has more or fewer columns than expected.
  • Columns are separated by the delimiter (default tab). NULL is the null string (default \N). Both are configurable.
  • COPY TO writes the null string without adding backslashes, and COPY FROM matches it before removing backslashes. The data value \N is therefore written \\N and is not confused with NULL.
  • A backslash, newline, carriage return or delimiter inside a value must be preceded by a backslash. Prefer \n and \r for newlines and carriage returns.
  • COPY FROM recognizes \b, \f, \n, \r, \t, \v, \ plus 1 to 3 octal digits, and \x plus 1 or 2 hex digits. Any other backslashed character stands for itself. COPY TO uses the named sequences for those control characters, but never emits octal or hex sequences.
  • Do not add unnecessary backslashes. The end-of-data marker \. and the null string are recognized before other backslash processing, so escaping . or N can produce one of them by accident.
  • Backslash sequences are interpreted after encoding conversion. Bytes given by octal or hex sequences must form valid characters in the database encoding.
  • End of data is signalled by CopyDone. A \. line is still recognized as a terminator in text-mode COPY IN, but this is deprecated, and it is not sent during COPY OUT.

CSV format

  • Values are separated by the delimiter (default comma). Backslash is not special, and text-format escapes do not apply.
  • A value is enclosed in the quote character (default ") if it contains the delimiter, the quote character, the null string, a carriage return or a line feed. Inside it, each quote or escape character is preceded by the escape character, which defaults to the quote character, so quotes are doubled by default. FORCE_QUOTE can also quote other non-NULL values on output.
  • NULL is the null string, unquoted, and a non-NULL value matching the null string is quoted. By default, NULL is an unquoted empty string and an empty string is "". Input follows the same rule, so compare against the null string before removing quotes. FORCE_NOT_NULL and FORCE_NULL change this for chosen columns on input.
  • All characters are significant, so whitespace around a value is part of the data.
  • Quoted values can contain carriage returns and line feeds, so one record can span several lines. Do not split records on newlines.
  • \. is not normally special when reading CSV. Servers before PostgreSQL 18 always treated an unquoted \. line as end of data, so COPY TO still quotes \. when it is alone on a line.

JSON format

Allowed only in COPY TO. Each row is one JSON object keyed by column name. SQL NULL is written as null, and so is a JSON or JSONB value that is the literal null, so the two cannot be told apart.

With FORCE_ARRAY, the output is one JSON array, so an individual CopyData is not a valid JSON document:

[
 {"id":1}
,{"id":2}
]

Asynchronous Messages

The server can send these without a client request. After startup, the client must be ready to accept them at any point, including while idle and during COPY, and should at minimum check for them before it starts reading a query response. During startup, the server sends none of them before AuthenticationOk. After AuthenticationOk, it sends ParameterStatus and can send NoticeResponse.

NoticeResponse

Layout is under Error and Notice Messages. Notices can come from outside events, such as a server shutdown request, and do not stop the current command. Display them or pass them to the application.

ParameterStatus

TypeDescription
Byte1('S')Message type
Int32Length
StringParameter name
StringCurrent value

Sent at startup and whenever the active value of a reported parameter changes. The cause can be SET, a rolled-back SET, or a configuration reload.

The currently reported parameters are application_name, client_encoding, DateStyle, default_transaction_read_only, in_hot_standby, integer_datetimes, IntervalStyle, is_superuser, scram_iterations, search_path, server_encoding, server_version, session_authorization, standard_conforming_strings and TimeZone. This set may change, so ignore unknown names. Older servers report fewer: default_transaction_read_only and in_hot_standby start in PostgreSQL 14, scram_iterations in 16, and search_path in 18. server_version, server_encoding and integer_datetimes cannot change after startup.

After SET, the message arrived after CommandComplete and just before ReadyForQuery. A SET and ROLLBACK inside one Query message produced none, since the value was unchanged by then. Separate messages produced one each.

Query Cancellation

To cancel a running query, open a new connection and send CancelRequest instead of StartupMessage. SSLRequest or GSSENCRequest can precede it. Any process holding the process ID and secret key can send it, so keep the key private.

TypeDescription
Int32Length: 12 + secret key length
Int32(80877102)Cancel request code
Int32Backend process ID, from BackendKeyData
BytenSecret key, from BackendKeyData (4 bytes before protocol 3.2; at most 256)

The server processes the request and closes this connection without any reply, even when the key does not match. The client cannot tell directly whether the cancel worked and must keep waiting on the original connection. If the cancel takes effect, the current command ends early with ErrorResponse. If it arrives too late, it has no effect.

Connection Termination

  • Normal: the client sends Terminate (X) and immediately closes the connection. The server then closes its end and exits.
  • Server-initiated: in cases such as an administrator-commanded shutdown, the server tries to send an error or notice giving the reason before it closes.
  • Failure: on an unexpected closure, clean up and optionally reconnect. Also close the connection on an unrecognizable message type, since it probably indicates lost message-boundary synchronization.

Any open transaction is rolled back in every case. If the client disconnects while a non-SELECT query is running outside a transaction block, the server will probably finish the query and may commit it before noticing.

Implementation Checklist

  1. Framing: read each whole message using its length before processing it, and marshal each whole message before sending it. Partial messages lose synchronization, so abandon the connection if I/O fails partway through one.
  2. State machine: accept any message whenever it could make sense. ErrorResponse, NoticeResponse, ParameterStatus and NotificationResponse can all appear between expected messages.
  3. Buffers: strings and field values have no predefined length limit, so use growable buffers. A client with a fixed buffer should read the full string and discard what does not fit. In extreme cases, the message length lets a receiver skip a message it cannot buffer.
  4. Encoding: strings use the session's client_encoding, not necessarily UTF-8. To get UTF-8, send client_encoding=UTF8 in StartupMessage, and track ParameterStatus in case it changes.
  5. Transaction status: use the ReadyForQuery status byte, since a BEGIN block is not closed by Sync.
  6. Protocol version: handle NegotiateProtocolVersion on the same connection, and size the cancel key from BackendKeyData.
  7. Encryption: N and ErrorResponse replies arrive before the server is authenticated. Follow the client's encryption policy instead of falling back automatically, because an attacker can forge these replies.
